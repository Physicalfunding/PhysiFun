# /dev — 開発フロー（ローカル）

Issue を起点に開発を進める。ブランチ作成から実装・検証・PR 作成・レビュー・修正まで。
ユーザーが画面の前にいるローカルセッション向けで、実装計画の合意（手順 5）と push・PR 作成（手順 11）でユーザーの返事を待つ。

クラウドセッション（`CLAUDE_CODE_REMOTE=true`）では `cloud-dev` skill を使う（待つ手順・ブランチ・PR の作り方が違う）。`cloud-dev` はこのスキルの PR body テンプレート（手順 10）・検証が落ちたときの対処（手順 7）・指摘の分類（手順 15）を参照している。

## 引数

```
/dev {Issue番号}
/dev              ← 番号なし
```

## フロー

### 1. 何をやるか確定

- **番号あり** → Issue の内容を取得し、要件を把握する（`gh issue view` は Projects (classic) の廃止で GraphQL のエラーになるため、REST を使う）

  ```bash
  gh api repos/Physicalfunding/PhysiFun/issues/{番号} --jq '.title, (.labels | map(.name)), .body'
  gh api repos/Physicalfunding/PhysiFun/issues/{番号}/comments --jq '.[] | .user.login + ": " + .body'
  ```

  - 「受け入れ要件」（古い Issue では「受け入れ条件」）のチェックリストを控える。ステップ 8 で 1 項目ずつ確かめる
  - 受け入れ要件が無い・何で確かめるか分からない書き方のときは、ステップ 4 で確認する
- **番号なし** → 「まず `/issue` で Issue を作成してください」と案内して**終了する**。Issue なしの開発は行わない

### 2. ブランチ作成

1. `main` を最新にする（`git switch main && git pull`）
2. Issue のラベル（type）と内容から `type/{issue番号}-slug` 形式のブランチ名を提案する
   - slug は英語の短い説明（kebab-case）
   - 例：`feat/42-leader-apply-form`、`fix/57-auth-session-crash`
3. ユーザーに確認してから `git switch -c` でブランチを切る

### 3. コンテキスト収集

Issue の内容に基づいて、関連するドキュメントとコードを読む。以下を優先的にチェック：

- `CLAUDE.md` — 禁止事項・推奨事項（必須）
- `docs/README.md` — ドキュメントの地図（ここから辿る）
- `docs/specs/01_system-architecture.md` — 技術スタック・レイヤー責務・命名規則
- `docs/product.md` — リリース計画・機能スコープ
- `../docs-repository/` — 該当する機能仕様
- 既存の関連コード（`apps/`、`packages/`）

何を読んだかを簡潔に報告する。

### 4. 質問（あれば）

仕様の曖昧な点や技術的な判断が必要な点があればまとめて質問する。
なければスキップして次へ進む。

### 5. 実装計画

以下をリストアップし、**ユーザーの合意を得てから**次に進む：

- 変更・新規作成するファイルの一覧
- 実装の手順（順序）
- 判断した設計方針（選択肢があった場合はその理由も）
- 受け入れ要件の各項目を、どの変更・テストで満たすか
- 差分の見込み。テストを含めて 200〜300 行が目安。大きく超えそうなら PR を分ける案を出す（最後の PR 以外は `Closes` ではなく `Refs #{番号}` で参照し、先にマージした PR で Issue が閉じないようにする）

合意が得られるまで実装に着手しない。

### 6. 実装

計画に沿って実装する。

- lint-on-edit hook が `.ts` / `.tsx` の書き込みごとに Prettier と ESLint（境界ルールを含む）を自動でかける。違反を指摘されたらその場で直す
- こまめに型チェックが通る単位で進める
- コミットは論理的な単位でまとめる（1 Issue = 1〜数コミット）
- UseCase を追加する場合は `add-usecase` skill の規範手順に従う

### 7. ローカル検証（CI と同じ順序）

`.github/workflows/ci.yml` のジョブ構成と一致させる。リポジトリのルートで実行する。
終了時には Stop hook（`verify-on-stop`）も `bun run check` を自動で実行し、失敗していれば終了が差し戻される。それに頼らず、ここで明示的に通しておく。

```bash
bun install --frozen-lockfile     # ロックファイル固定でインストール
bun run check                     # lint（web・admin・packages）→ format:check → typecheck → test（CI と同じ順）
bun run build                     # web ビルド
```

#### Docker がある環境のみ（infrastructure 結合テスト）
```bash
bun --filter @physifun/infrastructure test   # Testcontainers + vitest
```
> Docker が無い場合はここだけ CI に委ねてよいが、PR body に明記する。

#### 失敗したときの対応

| 失敗 | 対応 |
|---|---|
| `format:check` が落ちる | `bun run format` で自動整形 → 差分をコミット |
| `lint` が落ちる | 指摘箇所を修正。安易な `eslint-disable` は付けない |
| `typecheck` が落ちる | 型を直す。`any` / 非 null 断言での握りつぶし禁止 |
| `test` が落ちる | **実装かテストのどちらが正しいかを判断**してから直す |
| `build` が落ちる | サーバー / クライアント境界・env 参照位置を確認 |

すべて green になるまで次に進まない。

### 8. 受け入れ要件の確認

ステップ 1 で控えた受け入れ要件を、1 項目ずつ確かめる。

- 各項目について、満たしているかと、その根拠（テスト名・コマンドの結果・変更したファイル・画面での確認）を書き出す
- 満たしていない項目があれば、ステップ 6 に戻って実装する（直したらステップ 7 も通し直す）
- 計画の合意で別 Issue に回したなど、意図して満たさない項目は、理由を添えてユーザーに確認する
- 結果はステップ 10 の PR body の「受け入れ要件」に残す

すべての項目を満たすか、満たさない理由について合意できるまで次に進まない。

### 9. 品質レビュー（自動）

Workflow ツールで `full-review` ワークフローを実行する。
変更ファイルに対して arch-reviewer / security-reviewer / data-guardian を並列実行し、品質を検査する。

- レビュー結果に**「要修正」がある場合**は、PR 準備前に修正する
- 修正後、再度ローカル検証（ステップ 7）を通す
- 「注意」のみの場合は PR body に含めてユーザーに判断を委ねる

### 10. PR body 整形

以下を並列で確認する：

- `git status` — コミット忘れがないか
- `git log main..HEAD` — このブランチの全コミット
- `git diff main...HEAD --stat` — 変更の全体像

未コミットの変更がある場合は、コミットするか確認する。

以下のテンプレートで PR body を組み立てる。日本語で書く。

```markdown
## 概要
（何を変えたか 1〜3 文。Issue の「概要」をベースに、実装結果に合わせて調整）

## 関連 Issue
Closes #{番号}

## 変更内容
- （具体的な変更点を箇条書き。ファイル単位ではなく、機能単位で書く）

## 受け入れ要件
- [x] （Issue の項目をそのまま）— （根拠：テスト名・コマンドの結果・確認した画面）
- [ ] （満たしていない項目）— （理由：別 Issue #xx に回す など）

## 技術的な判断
- （設計上の選択や代替案があった場合、なぜこの方法を選んだかを簡潔に）

## 確認方法
- （実施したローカル検証コマンドと結果）

## スクリーンショット
（UI 変更がある場合のみ添付。なければセクションごと省略）

## 確認してほしい点
- （判断に迷った点・ユーザーに決めてほしい点）
```

- 「技術的な判断」は判断事項がなければ省略する
- 「スクリーンショット」は UI 変更がなければ省略する
- 「確認してほしい点」は無ければ省略する

### 11. ユーザーに承認を求める

PR 作成前に以下を表示して**ユーザーの承認**を得る：

- **タイトル**（Issue タイトルの流用）
- **ベースブランチ**（`main`）
- **body**（整形済み）
- **受け入れ要件の確認結果**（ステップ 8。満たしていない項目があればその理由）
- **品質チェック結果**（ステップ 9 の結果サマリー）

**push / PR 作成はユーザー承認後に行う。勝手に push しない。**

### 12. PR 作成

```bash
git push -u origin HEAD
gh pr create --title "タイトル" --body "body" --base main
```

PR URL を伝える。

### 13. レビューを自動発火

Agent tool を使ってレビューを別エージェントとしてバックグラウンドで起動する。
PR 番号と Issue 番号を渡す。実装者のコンテキストは引き継がない（独立した視点でレビューさせるため）。
受け入れ要件も、実装者とは別の目で確かめさせる。

```
Agent({
  description: "PR レビュー",
  prompt: "PR #{PR番号} の diff を独立した視点でレビューし、GitHub PR コメントとして指摘を残してください。Issue #{Issue番号} の受け入れ要件を満たしているかも 1 項目ずつ確かめてください。...",
  run_in_background: true
})
```

### 14. レビュー結果の取得

レビュー完了通知を受けたら、PR コメントを取得する（`gh pr view --comments` は手順 1 と同じ理由でエラーになるため、REST を使う）：

```bash
gh api repos/Physicalfunding/PhysiFun/issues/{PR番号}/comments --jq '.[] | .user.login + ": " + .body'                              # 会話のコメント
gh api repos/Physicalfunding/PhysiFun/pulls/{PR番号}/reviews --jq '.[] | select(.body != "") | .user.login + ": " + .body'           # レビューの本文
gh api repos/Physicalfunding/PhysiFun/pulls/{PR番号}/comments --jq '.[] | "\(.user.login) \(.path):\(.line // .original_line): \(.body)"'  # 行へのコメント
```

### 15. 指摘の吟味

取得したレビュー結果の各指摘を以下の基準で分類する：

| 分類 | 基準 | アクション |
|---|---|---|
| **修正する** | バグ・アーキテクチャ違反・セキュリティ問題・受け入れ要件の未達など、放置すべきでないもの | ステップ 16 で修正 |
| **見送る** | 好みの問題・過剰な抽象化提案・現状で問題ない指摘 | 理由をユーザーに報告 |
| **要確認** | 判断がつかないもの | ユーザーに判断を仰ぐ |

分類結果をテーブルでユーザーに提示し、「修正する」に分類した指摘と「要確認」の判断を**合意してから**次に進む。

### 16. 修正・再検証・プッシュ

修正すべき指摘がある場合：

1. 指摘に基づいてコードを修正する
2. ローカル検証（ステップ 7 と同じ）
3. 修正内容をコミットする（`fix: レビュー指摘対応` 等）
4. プッシュする（`git push`）
5. 修正サマリーをユーザーに報告する

修正すべき指摘がない場合：「全指摘確認済み、修正不要」と報告して完了する。

## 注意事項

- main への直接コミットは禁止。必ずブランチを切る
- 実装計画でユーザーの合意を得るまで実装に着手しない
- すべてのローカル検証が green になり、受け入れ要件を確かめ終わるまで PR 準備に進まない
- push / PR 作成はユーザー承認後。勝手に push しない
- クラウドセッションではこのスキルを使わず、`cloud-dev` skill を使う
- PR タイトルは Issue のタイトルをそのまま使う（二重管理を避ける）
- `Closes #{番号}` でマージ時に Issue を自動クローズする（1 つの Issue を PR 複数本に分けたときは、最後の PR 以外は `Refs #{番号}`）
- 変更内容はファイル一覧ではなく**機能単位**で書く
- push 前にリモートブランチの存在を確認し、既に push 済みなら `git push` のみ行う
- CodeRabbit の自動レビューが走る場合は、その指摘も同様に吟味する
