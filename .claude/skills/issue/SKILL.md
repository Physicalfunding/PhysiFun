# /issue — GitHub Issue 作成

ユーザーの指示から GitHub Issue を作成する。

## 手順

### 1. 意図と範囲をそろえる

`superpowers:brainstorming` を使い、何のために・誰のために・何ができたら完了かの 3 点をユーザーとそろえる。
使うのは前半だけ。意図を 1 問ずつ聞く → 理解を書き戻して直してもらう → 大きさを確かめる、までで止める（brainstorming の見出し名は版によって違うので、見出しではなくこの振る舞いで判断する）。

- 依頼の時点で 3 点が分かっていれば、質問せずに手順 2 へ進む（手順 4 で見せる body が理解の書き戻しを兼ねる）
- superpowers が無い環境（Skill に `superpowers:brainstorming` が無い）では、同じ 3 点を自分で確かめてから進む

Issue を作る段階なので、brainstorming の以下の部分は使わない。

- 大きさを分類して進め方を変えること（spike / 小さな変更 / 設計書が要る仕事、など）。大きさは手順 3 の「PR 1 本」の基準で判断する
- spec（設計書）ファイル（`docs/superpowers/specs/`）を書くこと。成果物は手順 3 の Issue body
- `writing-plans` に進むこと（実装計画は `dev` skill の手順 5 で作る）

### 2. 種別（type）を判定

ユーザーの指示内容、または明示的な指定から以下の 6 種別のいずれかを選ぶ。
迷ったらユーザーに確認する。

| type | ラベル | 用途 |
|---|---|---|
| `feat` | `feat` | 新機能の追加 |
| `fix` | `fix` | バグ修正 |
| `refactor` | `refactor` | リファクタリング・内部改善 |
| `docs` | `docs` | ドキュメント追加・修正 |
| `test` | `test` | テスト追加・修正 |
| `chore` | `chore` | 依存更新・CI・設定変更など |

### 3. Issue の内容を整形

以下のテンプレートで Issue の body を組み立てる。日本語で書く。

```
## 概要
（何をするか 1〜3 文）

## 背景・動機
（なぜ必要か）

## ユーザーストーリー
AS （誰）, I want （何をしたい）, so that （なぜ・得られる価値）

## 受け入れ要件
- [ ] （この Issue が「完了」と言える具体的な条件をチェックリストで。テスト・コマンド・画面での操作で確かめられる形に）

## 備考
（任意。技術的な制約や参考リンクなど）
```

- タイトルは簡潔に（日本語 OK、50 文字目安）
- 「備考」セクションは不要なら省略する
- 受け入れ要件は `dev` skill が PR を出す前に 1 項目ずつ確かめる。「きちんと動く」のような確かめようのない書き方にしない
- PR 1 本（テストを含めた差分 200〜300 行程度）に収まらない大きさなら、タイトルを `[親] ` で始めて親 Issue として作り、`split-issue` skill でサブ Issue に分ける

### 4. ユーザーに確認

作成前に以下を表示して確認を取る：

- **タイトル**
- **ラベル**（type 名をそのまま使う）
- **body**（整形済み）
- **提案ブランチ名**（`type/{issue番号}-slug` 形式。slug は英語の短い説明）

※ ブランチ名は Issue 番号が決まってから確定するので、この時点では `type/??-slug` と表示する。

### 5. Issue を作成

確認が取れたら `gh issue create` で作成する。

```bash
gh issue create --title "タイトル" --label "type" --body "body"
```

### 6. 結果を報告

作成後、以下を伝える：

- Issue URL（`gh` の出力から取得）
- 確定したブランチ名（`type/{実際の番号}-slug`）
- 「`/dev {番号}` で着手できます」と案内

## 注意

- ラベルが GitHub リポジトリに未作成の場合は `gh label create` で先に作る
- type 名はブランチ命名規約（`/dev`）と揃えること
