# プロダクト方針

## サービス概要

**フィジファン（フィジカルファンディング）**

お金ではなく、スキルと時間でプロジェクトを支援するマッチングプラットフォーム。
リーダーが古民家再生・米作り・DIY などのプロジェクトを立ち上げ、
サポーターがスキルや時間を提供してプロジェクトに参加する「フィジカルファンディング」の仕組みを実現する。

### ユーザー役割

| 役割 | 説明 |
|---|---|
| **リーダー** | プロジェクトを立ち上げ、スキル・時間の支援を募る人 |
| **サポーター** | スキルや時間でプロジェクトに参加する人 |
| **運営** | 応募・プロジェクトを審査する人（`apps/admin`、一般ユーザとは別の `AdminAccount`） |

> アカウントは 1 種類のみ。ロール配列（`SUPPORTER` / `LEADER`）で機能を段階的に解放する。

---

## チーム

| 役割 | 人数 | 担当 |
|---|---|---|
| エンジニア | 1名 | 設計・実装・インフラ |
| デザイン / 運営 | 2名 | UI デザイン・コンテンツ・審査・運営 |

**開発の基本方針:** まず自分たちが楽しめる MVP を素早く出す。完璧より速さを優先。

---

## スケール想定

- ローンチ時: 数十人規模
- 中期目標: 数百人規模
- 将来: 数千人規模（ただし「すぐではない」）

急激な成長は想定せず、段階的に対応する。

### 移行の方法

初回リリース → 一般公開の移行は **ランタイムのフィーチャーフラグではなく、コード変更リリース**で行う。環境変数による切替は行わない。応募フロー自体は 1 本のコードパスなので、一般公開時はサポーター向け新機能の追加のみで済む。

### 初回リリース（現在地）

**目的:** リーダー候補者を集めて審査し、承認後はリーダーがプロジェクトとサポート募集を準備できる状態まで引き上げる

状態: ✅ 実装済み / 🚧 未実装・実装途中

*リーダー応募の導線（非ログイン）*
- ✅ LP（ランディングページ）— リーダー募集の説明・魅力訴求
- ✅ リーダー応募フォーム（`/apply`）— 氏名・メールアドレス・プロジェクト案などを入力して送信
- ✅ CAPTCHA（Cloudflare Turnstile）+ IP レート制限 — スパム・メールボム対策
- ✅ 応募送信と同時に Account を自動発行（`PENDING_EMAIL_CONFIRMATION` / `SUPPORTER` ロール）
- ✅ Outbox 経由でアクティベーションリンク付きメール送信
- ✅ 利用規約・プライバシーポリシーページ

*アカウントのアクティベーション*
- ✅ メール内リンク → `/activate?token=xxx` でパスワード設定 → `ACTIVE` に遷移してログイン
- 🚧 `/my/application` で審査状況を確認（ページはあるが API がスタブで常に空）

*審査・承認（運営オペレーション、`apps/admin`）*
- ✅ 応募内容の確認・承認（`LEADER` ロール追加 + 承認通知メール）・却下（却下通知メール、Account は `SUPPORTER` のまま）
- ✅ プロジェクトの公開審査（承認・差し戻し・強制非公開）
- ✅ 運営メンバー管理・監査ログ・Outbox 管理
- 必要に応じて Gmail 等で応募者とやり取り（運用対応）

*オーファン Account の清掃*
- ✅ `PENDING_EMAIL_CONFIRMATION` のまま 72 時間経過した Account を cron で自動削除

*リーダー機能（ログイン後）*
- ✅ ログイン・ログアウト
- ✅ プロジェクト作成・編集（公開ステータスは `DRAFT` / `PENDING_REVIEW` / `PUBLISHED`、フェーズは `VISION` 〜 `ONGOING`。公開には運営審査が必要）
- ✅ マイページ（プロジェクト管理）・公開プロジェクトページ（`/projects/[slug]`、検索エンジンには非公開。slug は初回の公開承認で発行 — #262）
- 🚧 公開ページへの導線（マイページでの公開 URL 表示、承認メールのリンク先を `/projects/[slug]` にする）— 未着手
- 🚧 サポート募集の作成（活動参加募集 / スキル・モノ募集）と募集スケジュール管理（時間帯 + 同時刻定員）— #212
- 🚧 プロフィール編集・アイコン / SNS — #213
- 🚧 画像アップロード（Supabase Storage）— 実装はあるが UI 未接続
- 🚧 通知メールの正式テンプレート（現在は仮文面）
- LINE オープンチャット連携（事務局が作成 → リーダーに管理権限移行。運用対応）

**認証:** 応募フォームは非ログイン。アクティベーション後は通常のログインで利用。リーダー機能は `LEADER` ロール保持が前提

**スコープ外:**
- サポーターの自由登録（`/signup`）
- サポーター向けの閲覧・申請機能（プロジェクト一覧ページなど一般公開導線）

### 一般公開

**目的:** サポーターがプロジェクトを閲覧し、サポート募集に申請できる

*サポーター登録・閲覧*
- アカウント自由登録（`/signup`）— 応募フローとは別経路で Account を発行（`SUPPORTER` ロール自動付与）
- プロジェクト一覧・検索・詳細ページ
- サポート募集の閲覧

*サポート申請*
- サポートチケット（1h / 2h / 4h）を指定して申請
- 同伴人数指定
- 3 ステップフロー（入力 → 確認 → 完了）
- AUTO / MANUAL 承認モードに応じた確定フロー

*サポーター向け機能*
- マイページ（参加履歴・提供時間の累計）

*リーダー応募*
- 初回リリースと同じ `/apply` フォームを継続運用
- ログイン済みの場合は応募者情報（氏名・メール）を Account から自動取得してフォームを簡略化
- 非ログインからの応募も引き続き受け付ける

**認証:** サポーター自由登録（`/signup`）追加。リーダー応募（`/apply`）はログイン・非ログインどちらも可

## 補足

- **リターン**: 採用する。募集ごとにリーダーが設計する、サポーターへの返礼（必須、金銭リターンも一定条件下で可）。ドメイン実装はサポート募集（#212）と合わせて行う
- **メッセージング**: サポーター ↔ リーダー間のやり取りは初回リリースではサービス内に実装せず、LINE オープンチャットで代替する

業務側の詳細（ペルソナ・コンセプト・各機能の業務仕様）は別リポジトリ `docs-repository` の `docs/concept/concept.md` と `docs/mvp/202604_初回リリースに向けた計画/` を参照。

## 優先原則

1. **速度優先** — 完璧な設計より動くものを早く出す
2. **段階的拡張** — 次の段階の機能を先取りしない
3. **体験品質** — SEO より UX・スピードを重視（SEO が必要なのは LP のみ）
